# M16 — Single sign-on (OpenID Connect)

Status: approved by the user on 2026-09-22 ("yes for SSO"), including the two new dependencies and just-in-time accounts. Promoted from `docs/superpowers/drafts/sso-scoped-admins-spec.md` §2 and §4, revised against the code after M15. Builds on merged M1–M15.

**Scope.** The draft paired SSO with group-scoped administrators: admins limited to certain device groups. That half changes nearly every admin endpoint and is its own decision, so it stays in the drafts as the next candidate milestone. This milestone is sign-in only.

## 1. What and why

Console accounts are a local email and password, with optional authenticator codes. Organisations want their identity provider (Entra ID, Okta, Google, Keycloak and so on) to decide who can sign in and with what role, and they want leaving the company to mean leaving Retune. This milestone adds OpenID Connect sign-in:
- the role comes from a groups claim;
- an account is created on first sign-in;
- local accounts are kept as a way in when the identity provider is down.

## 2. Settings

| setting | default | meaning |
|---|---|---|
| `oidc_issuer` | — | the provider's issuer URL; discovery is `<issuer>/.well-known/openid-configuration` |
| `oidc_client_id`, `oidc_client_secret` | — | the client registered with the provider |
| `oidc_groups_claim` | `groups` | the ID token claim that lists the user's groups |
| `oidc_admin_groups` | — | comma-separated claim values that grant the admin role |
| `oidc_readonly_groups` | — | comma-separated claim values that grant read-only |
| `oidc_display_name` | `Sign in with SSO` | the button text |
| `oidc_disable_local_login` | `false` | refuse password sign-in entirely |

**Validation:**
- SSO is on when issuer, client ID and secret are all set. Setting only some of the three is a startup error.
- With SSO on, at least one of the two group lists must be set. Otherwise nobody could ever sign in, so that is a startup error too.
- `oidc_disable_local_login` without SSO is a startup error, because it would lock everyone out.
- The issuer must be https. The one exception is `http://localhost`/`127.0.0.1`, for trying things out.

The redirect URL to register with the provider is `<PUBLIC_URL>/api/admin/v1/oidc/callback`. Startup logs it.

## 3. Flow

The flow is the authorization code flow with PKCE (S256), `state` and `nonce`.

1. `GET /api/admin/v1/oidc/start`:
   - generates the state, the nonce and the PKCE verifier;
   - stores them in a `retune_oidc` cookie, sealed with the server's secret key under the context `oidc-login` (`secrets.Key.Seal`, AES-GCM, so the cookie can be neither read nor forged);
   - the cookie lasts 10 minutes and is `HttpOnly; Secure; SameSite=Lax`. It has to be Lax because the provider's redirect back to us is a cross-site navigation, and Strict would drop it;
   - then redirects (302) to the provider.
2. `GET /api/admin/v1/oidc/callback`:
   - unseals the cookie and checks that `state` matches;
   - exchanges the code with the verifier;
   - verifies the ID token with `go-oidc`: signature against the provider's keys, issuer, audience, expiry, and the `nonce` claim against the cookie's;
   - maps the groups claim to a role and signs the user in (§4);
   - clears the cookie, sets the usual `retune_session` cookie (unchanged, still `Strict`), and redirects to `/`.
3. **Failure:** any failure redirects to `/?sso_error=<code>` with no detail in the URL. It goes to the root, not `/login`: the console has no such route, and shows the sign-in page to anyone not signed in. The console turns the code into a sentence. The detail goes to the log, and to the audit log where §5 says so.

**Discovery** happens lazily, on the first `/oidc/start`, and is cached. A failed discovery isn't cached, so an identity provider that was down when the server started doesn't stop the server starting, and doesn't break SSO until a restart.

**Dependencies:** `github.com/coreos/go-oidc/v3` and `golang.org/x/oauth2`. Verifying ID tokens is security-critical, and a maintained implementation beats a hand-written JWT verifier.

## 4. Accounts

**Identity.** An SSO account is keyed by issuer and subject (`sub`), never by email:
- not every provider verifies email addresses, and matching on one would let whoever controls an address at the provider take over the local account that uses it;
- email is display only, kept up to date from the `email` claim (falling back to `preferred_username`), and must be present.

**Roles:**
- in any `oidc_admin_groups` group → `admin`; otherwise in any `oidc_readonly_groups` group → `read_only`; admin wins when a user is in both;
- the role is worked out again at **every** sign-in and written to the account, so moving someone between groups at the provider takes effect the next time they sign in;
- open sessions read the account on every request, so a changed role applies to them at once.

**Refusals and first sign-in:**

| situation | outcome |
|---|---|
| **No matching group, first time** | Refused; no account is created. |
| **No matching group, existing account** | Refused, and all of that account's sessions are deleted. |
| **First sign-in, with a matching group** | Creates the account, with `auth_source = 'oidc'`, no password and no authenticator secret. The provider handles MFA. |
| **Email already used by a local account** | Refused, with a message saying so. The two are never merged. An admin who wants to move a person to SSO deletes, or re-emails, the local account first. |
| **Account disabled in Retune** | Refused, as for local accounts. Disabling in Retune overrides the provider. |

**What SSO accounts can't do:**
- sign in with a password (the password form treats them as unknown, with the same timing);
- have a password or authenticator set or cleared in the console or CLI.

Disabling and enabling an SSO account still work.

**Signing people out.** Someone removed from the provider entirely never signs in again. Their open sessions last until they expire (`SESSION_TTL_HOURS`), or until an admin disables the account. This is documented.

**Local accounts** keep working unless `oidc_disable_local_login` is set. `bootstrap-admin` always works from the command line. With local login off, a local account can't sign in, so the way back in when the provider is down is to unset the setting.

## 5. Audit

- `admin.login`: new `method` detail, `local` or `oidc`.
- `admin.provisioned`: an account created by first sign-in, with the role.
- `admin.role_changed`: the role at sign-in differs from the stored one.
- `admin.login_refused`: an unmapped user, a local-email collision, or a disabled account, with the reason and the subject. Failures in the protocol itself (bad state, a bad token) are logged but not audited: anyone can make those happen, and a flood of them would bury real entries.

## 6. API and console

**API:**
- `GET /setup` also returns `sso: {enabled, display_name}` and `local_login: bool`.
- `POST /session` answers `403 local_login_disabled` when local login is off.
- Admin JSON gains `auth_source`.

**Console:**
- the sign-in page shows the SSO button when SSO is on, and hides the password form when local login is off;
- it turns `sso_error` codes into sentences;
- the Admins page shows each account's source, and doesn't offer password or authenticator actions for SSO accounts.

## 7. Schema

Migration `0014` adds to `admins`:
- `auth_source text NOT NULL DEFAULT 'local' CHECK (auth_source IN ('local','oidc'))`;
- `oidc_issuer text`, `oidc_subject text`;
- a unique index on `(tenant_id, oidc_issuer, oidc_subject) WHERE oidc_subject IS NOT NULL`;
- a check that an `oidc` account has an issuer and subject, and a `local` one has neither.

## 8. Testing

An in-process fake provider: an `httptest` TLS server with discovery, keys and a token endpoint, signing with its own RSA key via `go-jose`, which comes with `go-oidc`. It drives:
- a successful sign-in with the account created; a second sign-in reusing it; a role change on the provider taking effect;
- an unmapped user refused with nothing created; an existing account becoming unmapped losing its sessions;
- a collision with a local email refused;
- a disabled account refused;
- bad `state`, missing cookie, wrong `nonce`, wrong audience, wrong issuer, expired token, and a token signed by another key, each refused;
- local login disabled; an SSO account refused by the password form;
- password and authenticator changes refused for SSO accounts.

Config validation tests. Console tests for the sign-in variants and the Admins page. No real identity provider is used.
